## Proposed processing redesign (not approved for implementation)

The measured successful path serializes Events, pre-API audit, Scores and final audit MERGEs. After compaction, typical calls remain approximately 4.4s, 4.1s, 4.0s and 4.1s, before state reads, KQL, API and Kafka scheduling. Clustered high events arrive only a few seconds apart, so a preceding callback consumes much of the next event's budget. F8 CPU exhaustion is not established, and a larger SKU is not assumed to remove transaction/checkpoint latency.

The smallest proposed redesign keeps the existing Kafka input, per-event KQL, private per-event scoring API, F8 and named output tables. It reduces the success critical path from four table commits to two:

1. **Prepare and commit Events with recovery metadata.** Preserve existing Events columns and add a versioned recovery struct containing canonical payload/hash, original Kafka provenance, KQL snapshot/bounds/count/fallback and the exact scoring request. Commit the entire eligible batch before any API call. This replaces the separate pre-API audit durability barrier; it does not remove that information or make it merely in-memory.
2. **Call the API per event, then commit Scores with outcome metadata.** Preserve existing Scores columns and add a versioned outcome struct with request hash and stored score/attempt/result information. API failures retain Events and durably record failure/quarantine before acknowledging the source batch. The API continues to select and retain one random 1..100 score per original key, with changed payload rejected by 409.
3. **Project ProcessingAudit outside the output-critical path.** A separately checkpointed projection in the existing Spark environment reconstructs audit states from durable Events/outcome/failure records, using idempotent keys and monotonic state transitions. Audit completeness is required after drain. Any proposed maximum audit lag must be agreed explicitly; no unbounded lag or deletion of historical audit records is implied. Its resource contention still needs measurement.

Recovery rules are part of the change, not optional optimizations. A crash before Events commit permits re-enrichment because no HTTP call was allowed; after Events commit, replay must reuse the exact durable snapshot/request, without rerunning KQL. A crash after HTTP but before Scores commit repeats the identical request and reuses the API's durable score, not a new random draw. A committed Scores row prevents further scoring. Crashes before audit projection are repaired from the two committed stage records. A partially failed batch must not advance Kafka checkpoint until its success/failure states are durable. Duplicate envelopes are matched by original run/message plus canonical payload; conflicting application payloads quarantine without overwriting the first accepted snapshot. These are per-table transactions and at-least-once HTTP with durable idempotency, not cross-table atomicity or exactly-once delivery claims.

**Approval boundary:** implementing this requires approval for the added output metadata schemas, a changed authoritative recovery-state location and asynchronous audit materialization with an explicit lag/reconciliation policy.
